
### 第一部分：严格的代码审查工作流程 (CR Workflow)

为了保证“不破坏原有功能”，流程的管控比单纯看代码更重要。

#### 1. 提交前准备（Pre-Review / Author阶段）
*   **自动化卡点**：代码必须通过 CI/CD 管道的基础检查（Linter 零警告、静态代码分析如 SonarQube 通过）。
*   **自测与覆盖率**：提交的 PR/MR 必须包含对应的单元测试/集成测试。**增量代码测试覆盖率要求不低于 85%**（核心模块需 100%）。
*   **自我审查 (Self-Review)**：作者必须自己先过一遍代码，并在 PR 描述中清晰说明：背景、架构变更点、核心逻辑位置、已知风险及应对策略。
*   **原子化提交**：每个 PR 必须是单一职责的（一个 Bugfix 或一个 Feature），严禁包含多个无关修改（如顺手改了其他模块的格式），以缩小爆炸半径。

#### 2. 审查执行阶段 (Reviewing / Reviewer阶段)
*   **自顶向下审查**：
    *   *第一步：* 看接口和数据模型（API 定义、DB Schema）。
    *   *第二步：* 看架构设计和设计模式（模块职责划分）。
    *   *第三步：* 看核心算法、并发逻辑、异常处理。
    *   *第四步：* 看细节实现（变量命名、边界条件）。
*   **评论规范**：所有 Review 意见需分级（例如：`[Blocker]` 必须改、`[Optimization]` 建议优化、`[Nitpick]` 吹毛求疵的格式问题）。

#### 3. 修复与优化阶段 (Refactor & Fix阶段) **【关键：确保不影响功能】**
*   **测试先行 (TDD) 原则**：如果 Reviewer 提出优化建议，作者在修改前，**必须确保该逻辑已有完善的单元测试覆盖**。如果没有，先补齐测试，保证测试通过，然后再进行重构优化，最后再次运行测试确保绿灯。
*   **灰度与开关控制**：对于核心业务链路的深度优化，建议引入 Feature Flag（特性开关），确保线上随时可以回滚到旧逻辑。

#### 4. 批准与合并 (Approval & Merge)
*   至少需要 2 名高级工程师 Approve（`+2` 机制）。
*   任何后续的代码更改（即使是修复 Review 意见），都必须重新触发 CI/CD 和自动化回归测试。

### 第二部分：高级代码审查清单 (Senior CR Checklist)

这份清单将按文件、按模块严格执行。

#### 一、 架构与设计合理性 (Architecture & Design)
*   [ ] **单一职责 (SRP)**：该类/函数是否只做了一件事？有没有出现“上帝类 (God Class)”或超过 200 行的臃肿函数？
*   [ ] **依赖倒置与接口隔离**：高层模块是否依赖了底层具体实现？是否可以通过依赖注入 (DI) 或接口来解耦？
*   [ ] **状态管理**：对象是否尽可能地保持了无状态 (Stateless) 或不可变 (Immutable)？全局变量/单例模式的使用是否真正必要且安全？
*   [ ] **复用性与防腐败 (DRY & ACL)**：是否存在复制粘贴的重复代码？与第三方系统交互时，是否有防腐层 (Anti-Corruption Layer) 进行数据模型隔离？
*   [ ] **扩展性 (OCP)**：面对未来可能的需求变化，现有代码是否符合“对扩展开放，对修改封闭”？（例如：是否使用了策略模式替代过多的 `if-else`/`switch`）。

#### 二、 鲁棒性与异常处理 (Robustness & Reliability)
*   [ ] **错误不被吞噬**：所有的 `catch` 块是否都妥善处理了异常？严禁空的 `catch` 块或仅打印日志后继续执行（除非明确是降级逻辑）。
*   [ ] **精准捕获**：是否捕获了过大的异常类（如直接 `catch Exception`）？必须精确捕获具体的异常类型。
*   [ ] **边界与极端情况 (Edge Cases)**：
    *   输入为空、`null`、`0`、负数、空字符串、极大值时的处理。
    *   集合/列表为空时的迭代处理。
    *   可能引发除数为 0 或溢出的算术运算。
*   [ ] **并发与线程安全**：
    *   共享资源的访问是否加锁或使用了并发安全的集合？
    *   是否存在死锁风险（锁的获取顺序不一致）？
    *   事务的范围是否过大？是否合理配置了事务隔离级别和传播机制？
*   [ ] **资源泄漏**：文件流、数据库连接、网络套接字、锁资源是否在 `finally` 块或使用 `try-with-resources` (或等效语法) 中被正确释放？

#### 三、 性能与扩展性 (Performance & Scalability)
*   [ ] **算法复杂度**：循环嵌套层数是否过深？是否有明显的 $O(n^2)$ 及以上的低效遍历？能否用 Hash Map/Set 等数据结构用空间换时间？
*   [ ] **数据库与 I/O 优化**：
    *   是否存在 `for` 循环里查数据库/调用 RPC 的情况（N+1问题）？是否可以批量 (Batch) 处理？
    *   SQL 查询是否命中索引？是否查了不需要的字段（`SELECT *`）？
*   [ ] **内存管理**：是否在循环中频繁创建大对象？是否有潜在的内存泄漏（如未清理的 ThreadLocal、全局长生命周期的集合缓存）？
*   [ ] **超时与重试逻辑**：所有外部 RPC/HTTP/DB 调用是否都设置了合理的 Timeout？失败是否有重试机制？重试操作是否是**幂等 (Idempotent)** 的？

#### 四、 安全性 (Security)
*   [ ] **注入防御**：SQL、OS 命令、日志打印中，所有的外部输入是否都进行了转义、参数化校验或消毒 (Sanitization)？
*   [ ] **权限越权**：数据访问接口是否不仅校验了“用户已登录”，还校验了“该用户有权访问该具体资源”（防水平/垂直越权）？
*   [ ] **敏感数据**：代码中是否硬编码了密钥、Token、密码？日志打印中是否脱敏了用户隐私信息（手机号、密码、卡号）？

#### 五、 测试覆盖与可测性 (Testing & Maintainability)
*   [ ] **可测性**：代码是否容易编写单元测试？如果很难 mock，说明代码耦合度过高，必须重构（提取接口或剥离外部依赖）。
*   [ ] **测试用例质量**：测试是否只跑了 Happy Path（正常流程）？是否包含了异常分支和边界测试？断言 (Assert) 是否严格有效？

#### 六、 语法规范与代码整洁 (Syntax & Clean Code)
*(注：这部分主要靠自动化，人工做兜底核查)*
*   [ ] **命名规范**：变量/函数名是否做到了“名如其意”（Intent-Revealing）？严禁 `a`, `b`, `temp`, `data` 等模糊命名。
*   [ ] **语言特性**：是否正确且巧妙地使用了当前编程语言的特性（如 Python 的列表推导式、Java 的 Stream API、Go 的 defer/channel）？是否存在已废弃 (Deprecated) API 的调用？
*   [ ] **圈复杂度 (Cyclomatic Complexity)**：函数的条件嵌套是否过深（超过 3 层）？是否可以通过提前返回 (Early Return) 来扁平化代码？
*   [ ] **注释价值**：注释是否在解释**“为什么这样做 (Why)”**，而不是在解释“这段代码在干什么 (What)”（代码本身应该能解释 What）？是否有遗留的 `// TODO` 或大段被注释掉的死代码？
