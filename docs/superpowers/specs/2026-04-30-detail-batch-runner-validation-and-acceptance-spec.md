# Detail Batch Runner Validation And Acceptance Spec

## 1. Purpose

This document defines how generated detail batch-runner scripts should be validated and accepted before they are treated as shippable outputs.

The target artifact is:

- a standalone Python batch orchestration script generated by the platform

This spec is necessary because stage-2 scripts are operationally sensitive. A script that is merely syntactically valid is not sufficient; it must also preserve the approved orchestration contracts.


## 2. Scope

This spec covers:

- static validation
- contract validation
- behavioral acceptance
- smoke validation
- warning and rejection criteria

This spec does not define:

- the generator request contract
- the detail extractor CLI internals
- the detail task table schema in detail


## 3. Validation Objectives

The validation pipeline must ensure that the generated script:

1. is structurally complete
2. respects the approved task lifecycle model
3. calls the detail extractor CLI correctly
4. keeps detail extraction outside the batch runner
5. is suitable for local operator execution


## 4. Validation Layers

The script should pass four validation layers:

1. syntax validation
2. static structure validation
3. contract validation
4. behavioral smoke validation


## 5. Layer 1: Syntax Validation

### 5.1 Required checks

The generated script must:

- parse as valid Python
- compile without syntax errors

### 5.2 Failure behavior

If syntax validation fails:

- generation result must be rejected


## 6. Layer 2: Static Structure Validation

### 6.1 Required top-level classes

The script must contain:

- `Config`
- `TaskRepository`
- `CliInvoker`
- `TaskRunner`
- `BatchExecutor`

### 6.2 Required functions

The script must contain:

- `main`

### 6.3 Required runtime constructs

The script must reference:

- `ThreadPoolExecutor`
- `subprocess.run`
- `sqlite3`

### 6.4 Required module boundary

The script must include a `__main__` entry block.

### 6.5 Recommended but optional constructs

The script should preferably include:

- `argparse`
- structured logging setup
- dataclasses for task/result/summary records


## 7. Layer 3: Contract Validation

### 7.1 Task-state contract

The script must use only approved state names:

- `pending`
- `running`
- `succeeded`
- `failed_retryable`
- `failed_terminal`
- `skipped`

Scripts introducing ad hoc states should be rejected unless the contract itself has changed.

### 7.2 CLI-boundary contract

The script must:

- invoke the external detail extractor CLI
- pass URL, task ID, output root, and JSON output mode

The script must not:

- directly import and call detail extraction runtime modules by default
- embed detail extraction logic

### 7.3 Database contract

The script must reference:

- the configured list result table
- the configured task table
- the configured `record_id` field
- the configured `detail_url` field

### 7.4 Result-summary contract

The script must be able to consume the expected CLI summary fields, especially:

- `status`
- `task_id`
- `task_dir`
- `content_markdown_path`
- `pdf_snapshot_path`
- `attachments_dir`
- `error_code`
- `error_message`


## 8. Layer 4: Behavioral Smoke Validation

Behavioral validation should be run on a lightweight fixture database and a controlled CLI stub or reference implementation.

### 8.1 Required scenarios

The script should be exercised through at least these scenarios:

1. sync new tasks from list results
2. skip rows with empty detail URLs
3. claim pending tasks
4. mark successful tasks
5. mark retryable failures
6. stop retrying beyond retry ceiling
7. resume from database state on rerun

### 8.2 CLI stub mode

The easiest path is to use a CLI stub that:

- accepts the same arguments
- emits deterministic JSON summaries
- returns configurable exit codes

This allows validation without requiring the full production detail extractor implementation.


## 9. Rejection Criteria

The generated script must be rejected if any of the following is true:

1. syntax is invalid
2. required classes or `main` are missing
3. no CLI subprocess invocation exists
4. `ThreadPoolExecutor` is absent without explicit contract change
5. task claiming appears to be distributed into workers instead of centralized
6. the script directly imports detail extraction runtime modules as the execution path
7. unsupported state names are introduced
8. configured database fields are not referenced correctly


## 10. Warning Criteria

The generated script may still be accepted with warnings if:

1. optional CLI arguments are omitted
2. dry-run support is missing when only recommended, not mandatory
3. limit support is missing when only recommended, not mandatory
4. comments are sparse or style is suboptimal but the contract is preserved


## 11. Suggested Static Checks

Recommended static checks:

- class-name presence check
- function-name presence check
- AST-level import inspection
- AST-level call inspection for:
  - `subprocess.run`
  - `ThreadPoolExecutor`
- string-literal check for required statuses
- string-literal check for CLI executable name
- reference check for configured table and field names


## 12. Suggested Behavioral Acceptance Checklist

A generated script is considered operationally acceptable when:

1. it can create the task table if missing
2. it can sync from the list result table
3. it can claim tasks in the main thread
4. it can run CLI subprocesses concurrently
5. it can parse stdout JSON summaries
6. it can write success and failure outcomes back into SQLite
7. it can produce a final run summary


## 13. Suggested Validation Output Shape

Recommended validation result schema:

```json
{
  "passed": true,
  "errors": [],
  "warnings": [],
  "checks": [
    {"name": "syntax", "passed": true},
    {"name": "required_classes", "passed": true},
    {"name": "cli_boundary", "passed": true},
    {"name": "task_states", "passed": true}
  ]
}
```


## 14. Acceptance Levels

Recommended acceptance levels:

### Level A: static-valid

- syntax + structure + contract pass

### Level B: smoke-valid

- Level A plus behavioral smoke checks pass

### Level C: ship-ready

- Level B plus approved operator-facing logs and output clarity

The recommended platform threshold for normal delivery should be:

- at least Level A for early internal generation
- Level B for implementation handoff
- Level C for production-facing delivery


## 15. Relationship To The Capability Pipeline

This validation spec should be wired into:

- `Generate Detail Batch Runner`

as a required post-generation step, not as an optional afterthought.

The generator should fail closed when mandatory validation fails.


## 16. Final Recommendation

Treat validation as part of the product capability itself.

The stage-2 script should only be considered acceptable when it preserves:

- the task-state contract
- the CLI boundary
- the deterministic concurrency model
- the standalone operator-runner shape

Anything less risks turning the generated artifact into an unreliable operational script.
